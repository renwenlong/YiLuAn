## 1. 背景与目标

医路安目前**微信小程序**与 **iOS** 两端界面文案全部为中文硬编码，无任何国际化（i18n）基础设施。帝君要求：**为界面增加语言切换能力，仅支持「中文 / 英文」两种语言。**

**目标（一句话）：** 用户可在设置页手动切换界面语言（简体中文 ⇄ English），切换后当前端全部用户可见界面文案即时（或重启后）以所选语言呈现，选择持久化。

**业务价值：** 支撑海外/英文用户使用，为后续国际化扩张打基础。

## 2. 范围定义（Scope）

### 2.1 本次范围内（In Scope）

| 端 | 内容 |
|----|------|
| **微信小程序** | 全部用户可见界面文案支持中/英切换；设置页新增语言切换入口 |
| **iOS** | 全部用户可见界面文案支持中/英切换；设置页新增语言切换入口 |

- **支持语言：** 简体中文（`zh-Hans` / `zh-CN`）、英文（`en`）——**仅此两种**。
- **切换方式：** 用户在 App 内**手动**切换（不做「跟随系统语言」为唯一来源，但首次默认值可参考系统语言，详见 §4）。
- **文案范围：** 所有**用户可见**的静态界面文案 + 动态拼接文案 + 状态/枚举展示文案（订单状态、服务类型名等前端映射文案）。

### 2.2 本次范围外（Out of Scope）—— 明确排除，非隐性搁置

以下项**本期不做**，理由与后续建议一并列出，供帝君决策是否单开 task：

1. **admin-v2 管理后台**（React+antd）——帝君指令仅点名「微信小程序 和 iOS」，admin 后台面向内部运营，本期不纳入。*(技术上最轻：antd `ConfigProvider` 已接 locale，zustand 现成，后续单独立项 0.5 人日可完成。)*
2. **后端 API 返回的中文错误消息本地化**——后端 `raise` 出用户可见中文错误消息（如「订单状态不允许请求开始服务」「该订单已退款，请勿重复操作」）。本期界面切到英文时，**这些后端错误文案需有本地化策略**。
   - **🔴 2026-07-09 架构师魈 review 更正（evidence-first 核 main HEAD，PM 采纳）：**原 PRD 称「后端无 error_code 机制」与代码实况不符——`backend/app/core/error_codes.py`（机器码注册表）+ `AppException(error_code=)` envelope + iOS `APIClient.swift` 按 code dispatch **均已存在**（infra 已建 ~70%，仅 raise 站点未接线 + 微信侧 dispatcher 缺失）。故**方案 B「从零建体系」是幻影成本**。真正选择为：
     - **方案 A（脆弱）**：前端持 error message **中文文本** → i18n key 映射，命中即替换，后端不改。成本低但**后端一改文案即静默击穿**（文本匹配脆弱）。
     - **方案 C（推荐，架构师意见）**：**复用既有 `error_code` 通路**——后端 raise 站点 attach error_code（≈16 处，可枚举，接线成本低），前端按 **code** 取译文。抗漂移、顺架构，iOS 侧已 code-ready。
   - **本 PRD 默认改推方案 C**（详 `docs/adr/ADR-0062-i18n-backend-error-localization-strategy.md`，三方案对比+证据命令）。待帝君拍板 A vs C。
   - **魈 review 重点 2 给 design：**①微信侧 dispatcher（`wechat/services/request.js` docstring 声称但**实际不存在**）需新增 task 对齐 iOS；②术语表 §7 需扩展纳入 error_code→中/英 映射。
3. **图片/富文本/运营配置类内容**（如 banner 图内嵌文字、后台可配的公告文案）——本期只做**代码内静态/映射文案**，图片文字与运营内容不做多语言。
   - **⚖️ 2026-07-10 PM 裁决（胡桃 DEV-002 抽 key 时提出 AC-3 边界问题，PM 拍板）：【法律条款正文本期不译】**——微信 `pages/legal/privacy` + `pages/legal/terms` 两页的**法律条款正文**（隐私政策/用户协议全文，实测 ~109 行：privacy 62 + terms 47）**加白名单排除，本期不抽 key、不英译**。
     - **理由**：①合规风险——隐私政策/用户协议英文版有法律效力含义，错译可致条款歧义/监管风险，必须走法务/专业法律翻译审校，非开发直译/机译；②帝君指令是「界面」语言切换，法律正文是内容文档非 UI 文案，归本条排除口径。
     - **仍需翻译（属 UI 层，不在排除内）**：两页的**页面标题/导航标题、入口入口项（设置页「隐私政策」「用户协议」链接文案）、按钮**仍抽 key 翻译。排除的仅是条款**正文段落**。
     - **降级体验（可接受已知限制）**：英文模式下法律页正文暂显中文；开发可在正文顶部加一条 UI 提示（可翻译）如「英文版法律条款即将上线」。
     - **后续 backlog**：法律文本英译（法务审校）单独立项，不入本期。iOS 同口径（如有对应法律正文页同步白名单）。
4. **RTL（从右到左）布局**、**多语言之外的本地化**（货币、日期格式深度本地化）——本期不做；日期/金额沿用现有展示，仅文字标签翻译。

> 范围外项若帝君要求纳入，**新建 task**，不在本 PRD 追加。

### 2.3 跨端一致性要求（关键，避免各端各译）

- **必须先定义跨端「文案 Key 命名规范 + 中英词表（术语表）」**，微信与 iOS 共用同一份术语翻译（如「陪诊师」统一译 `Companion`、「患者」统一译 `Patient`、订单状态统一译法），避免两端对同一术语译法漂移。
- 术语表作为需求交付物的一部分，架构师 design 阶段据此定义 key 结构，两端各自实现但**术语译文一致**。

## 3. 现状基线（供设计/开发/测试参考，实测证据）

| 端 | 框架 | i18n 现状 | 可见文案量级 | 语言入口现成落点 | 全局状态落点 |
|----|------|-----------|--------------|------------------|--------------|
| 微信 | 原生小程序（非 Taro/uni） | **无库、无机制**，wxml 内联中文 + JS 层中文串 | 数百~上千条（wxml ~765 + JS ~1091 处中文，去重后数百上千） | `pages/profile/settings/index`（设置页，分包 `u-settings`） | `store/index.js`（自研 store，可挂 `language` 字段） |
| iOS | SwiftUI，XcodeGen | **零本地化资源**，`Text("中文")` 字面量 ~131 处 View 内、全量中文字面量 ~690 处；无 `.lproj`/`.xcstrings`/`knownRegions` | 数百条 | `Features/Settings/Views/SettingsView.swift` | 需新建语言状态（`@AppStorage`/EnvironmentObject），`project.yml` sources 接 `.xcstrings` |

**技术难点提示（非需求约束，供架构师评估）：**
- iOS 零基础设施 + 690 处硬编码，改造量最大，需从 0 搭 `.xcstrings` 并全量替换。
- 微信原生 wxml 是静态模板，不支持函数插值 key，通用做法是全局 `t` 字典 + `mixin`/`setData` 注入，覆盖全部页面与组件（含分包）。
- 两端均存在**动态拼接文案**（如微信 `切换为{{...}}`、`当前：{{...}}`；iOS `验证码已发送至 +86 \(phone)`），需支持带参数的占位翻译（如 `t('otp.sentTo', {phone})`），不能简单字符串替换。

## 4. 功能需求（Functional Requirements）

### FR-1 语言切换入口
- 微信、iOS 各自在**设置页**提供「语言 / Language」入口，进入后可选「简体中文 / English」两项，单选。
- 当前生效语言需有明确选中态标识。

### FR-2 语言默认值（首次安装/未设置时）
- 首次使用、用户从未手动选择过语言时：**默认取系统语言**——系统为中文环境 → 默认中文；系统为非中文环境 → 默认英文。
- 用户一旦手动选择，则以用户选择为准，不再被系统语言覆盖。

### FR-3 切换即时性
- **微信**：切换后**当前页及后续所有页面**立即以新语言呈现（依赖 store 通知刷新）。允许「当前停留页需返回/重进才完全刷新」作为可接受降级，但**至少设置页自身 + 重新进入的页面**必须立即生效。
- **iOS**：切换后**至少重新进入的界面**以新语言呈现；若采用需重启 App 生效的方案，必须在切换时明确提示用户「重启后生效」并可接受。（优先做到无需重启即时生效，具体由架构师定方案。）

### FR-4 持久化
- 用户所选语言**持久化到本地**（微信 `Storage`；iOS `UserDefaults`/`@AppStorage`），冷启动后保持上次选择，不重置。

### FR-5 覆盖完整性
- 所选语言下，该端**所有用户可见静态界面文案**（页面标题、按钮、标签、占位符 placeholder、空状态提示、Tab 名、导航标题、弹窗/Toast/Alert 文案）均以所选语言呈现。
- **动态拼接文案**（含变量占位）正确按语言拼接，语序符合目标语言习惯（不是把中文语序直译）。
- **状态/枚举展示文案**（订单状态、服务类型「全程陪诊/半程陪诊/代办跑腿」、角色「患者/陪诊师」等前端映射文案）按语言呈现。

### FR-6 后端错误文案本地化（对应 §2.2；默认方案 C，待帝君拍 A vs C）
- 对**高频后端错误消息**（至少覆盖：订单状态流转类、支付/退款类、资质/分享类中用户最可能遇到的），前端在英文模式下做客户端映射翻译兜底；未覆盖的低频错误允许回退显示后端原文（中文），但需在测试报告中列出未覆盖清单。

### FR-7 无回归
- 切换语言功能上线后，**中文模式下现有所有界面与文案与改造前保持一致**（不得因抽 key 导致中文文案错漏、串位、丢失）。

### AC-2（语言切换基本流 — 母口径，后续 test task 分端细化）
- **微信**：
  1. 进入「我的」→「设置」，存在「语言 / Language」项；点击展示「简体中文 / English」两选项，当前语言有选中态。
  2. 切到 English → 设置页自身文案立即变英文；返回「我的」tab，页面文案为英文。
  3. 杀掉小程序重进 → 语言仍为 English（持久化生效）。
  4. 切回简体中文 → 文案恢复中文，与改造前一致（无错漏/串位）。
- **iOS**：
  1. 进入 设置页（SettingsView），存在「语言 / Language」项；可选「简体中文 / English」，当前语言有选中态。
  2. 切到 English → 界面文案为英文。**⚠ 切换即时性预期以 design 阶段架构师拍定的唯一方案为准（二选一，不得二义）**：
     - **方案①即时生效**：切换后重新进入的界面即为英文，无需重启，测试预期=「返回上级/重进页面即英文」；
     - **方案②重启生效**：切换时必须弹出「重启后生效」提示，测试预期=「杀进程重启后界面为英文，且切换时确有提示」。
     - design 未拍定前此条不可测；架构师在 ADR 明确选①或②，测试员据 get_task 最新 AC 执行（届时本条会被 design 收敛为单一预期）。
  3. 冷启动 App → 语言仍为 English（持久化生效）。
  4. 切回简体中文 → 文案恢复中文，与改造前一致。

### AC-3（覆盖完整性抽检 — 母口径）
- 每端至少抽检 **8 个核心页面**（覆盖：登录/角色选择、首页、下单/服务选择、订单列表、订单详情、消息/聊天、我的、设置），在 English 模式下**无残留中文**（后端低频错误文案除外，且需登记）。

### AC-4（默认语言）
- 模拟器/设备系统语言设为英文 + 全新安装（清除本地存储）→ 首次进入默认 English。

### AC-5（无回归）
- 中文模式下，改造后与改造前核心页面文案逐屏比对无差异（测试员以改造前截图为基线）。
- 两端原有单测/E2E（微信 Jest、iOS XCTest）全绿。

> **每条 test task 的 AC 由架构师/测试员在拆分时补足到「操作步骤 + 预期结果」粒度**（如「点击设置页语言项 → 弹出含『简体中文』『English』的选择器，『简体中文』左侧显示对勾」）。

### 7.5 带占位符的句式模板（Interpolated Message Templates）—— 动态拼接文案专用

> 刻晴 review 指出：§7.1~7.4 只有词条，缺带变量的**句式**译法。动态拼接文案的语序在中英文不同，必须按目标语言习惯组织，不能词条直拼。以下为句式基线，`{var}` 为运行时占位。架构师据此定义带参 key（如 `t('otp.sentTo', {phone})`），测试按此校验语序与占位。**架构师/开发在实现中发现新句式需回补本表，不得各自拼。**

| 场景 / key 建议 | 中文模板 | English 模板 | 占位 |
|-----------------|----------|--------------|------|
| `otp.sentTo` | 验证码已发送至 +86 {phone} | Code sent to +86 {phone} | phone |
| `role.switchTo` | 切换为{targetRole} | Switch to {targetRole} | targetRole(译文取 §7.1) |
| `role.current` | 当前：{role} | Current: {role} | role |
| `order.countUnit` | {count} 个订单 | {count} order(s) | count(英文注意单复数,≤1 用 order,>1 用 orders) |

## 9. Review 驱动的 design 阶段必解条件（刻晴 review 提出，PM 已采纳）

> 以下 4 项为测试员刻晴对验收母口径的可测性 review，PM 全部采纳。它们**不阻塞帝君审批**（AC-6 已将详细 AC 授权 design 细化），但**架构师拆 test task 前必须在 design/ADR 中给出结论**，否则回归验收会卡：

1. **【AC-5 无回归基线】（最大坑）**：iOS 现只有 XCTest 单测、无 snapshot/XCUITest UI target；微信 `miniprogram-automator` smoke **不在 CI 跑**且只有结构 `toMatchSnapshot`、无 image-snapshot。→ 「以改造前截图为基线逐屏比对」当前纯手动。**架构师定：**接受人工截图基线（则需明确截图清单/时机/存放），还是新增快照测试设施作为 dev task。
