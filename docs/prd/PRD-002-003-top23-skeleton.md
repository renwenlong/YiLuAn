# PRD-002: Top2 — 陪诊责任险 + 电子服务合同

> **状态**: 骨架 v0.1（PM 凝光出）
> **决策依据**: 帝君 2026-06-03 拍板 "本周全部代码交付，触发门作废"，本 PRD 解锁开发
> **关联 task**: BACKLOG-TOP23-OBSERVEpm（uuid 491b2ea0-84bb-4b49-9bf3-4ad3fccac222）
> **本周交付边界**: 后端 API 骨架 + admin 配置入口（vendor 接入、上线流程下迭代）

## 1. 业务目标

降低用户下单顾虑，构建合规护城河。
- **保险**: 陪诊师服务时段内意外/责任覆盖，事故有据可循
- **合同**: 下单即生成电子服务合同，权责清晰、可追溯、合规可查

## 2. 用户故事

- **U-2-1（用户）**: 我下单陪诊时能看到"本单含责任险（保额 X 万）"标识，知道出事有保障
- **U-2-2（用户）**: 下单成功后能在订单详情查看/下载电子合同 PDF
- **U-2-3（陪诊师）**: 接单后能看到本单保险覆盖范围
- **U-2-4（admin）**: 后台能配置保险产品、保额、合同模板版本
- **U-2-5（admin）**: 后台能查询任一订单的保单号、合同 hash、签署时间

## 3. 功能范围（本周交付）

### 3.1 必交付（代码 done）
| 模块 | 内容 | 边界 |
|---|---|---|
| 保险数据模型 | `insurance_policy` 表（订单关联、保额、状态、vendor占位、保单号占位） | 表+CRUD API，不接真实 vendor |
| 合同数据模型 | `service_contract` 表（订单关联、模板版本、内容 hash、签署时间、PDF 路径） | 表+生成逻辑，PDF 用现有 reportlab |
| 合同模板引擎 | 模板渲染（订单字段填充 + 双方签字位 + 条款版本） | 单一模板 v1，admin 可上传新版 |
| 下单流程接入 | 下单成功 → 同步生成合同 + mock 投保（写 policy_no=PENDING） | 投保异步任务占位 |
| 订单详情透出 | 用户/陪诊师订单详情 API 返回保险摘要 + 合同下载链接 | 字段加入现有响应 |
| admin 配置 | 保险产品 CRUD + 合同模板 CRUD + 订单查保单/合同 | 接 admin-h5（走 ADMIN-V2 骨架） |

### 3.2 下迭代（非本周）
- vendor 真实对接（保险公司 API、电子合同 CA 签章）
- 理赔流程、合同变更/作废流程
- 用户端签字交互（本周用"下单即默认接受"）

## 4. 验收标准

| AC | 标准 | 验证方式 |
|---|---|---|
| AC-1 | 下单成功 5s 内 `service_contract` 记录生成且 hash 非空 | 单元测试 + e2e |
| AC-2 | 下单成功 5s 内 `insurance_policy` 记录生成（状态=pending） | 单元测试 |
| AC-3 | 订单详情 API 返回 `insurance.coverage` 和 `contract.download_url` 两字段 | API 契约测试 |
| AC-4 | 合同 PDF 可下载，包含订单号/双方信息/服务条款/生成时间 | 人工+自动渲染断言 |
| AC-5 | admin 能 CRUD 保险产品和合同模板，权限受 ADMIN_API_TOKEN 控制 | admin-h5 冒烟 |
| AC-6 | admin 输入订单号能查到 policy_no/contract_hash/signed_at | admin-h5 冒烟 |
| AC-7 | 9 字段契约不漂移（保险/合同新字段不污染 share_* 字段） | CI GUARDED_FIELDS 检查 |

## 5. 非功能要求

- 合同 PDF 生成 P95 < 2s
- 下单流程不因合同/保险失败而失败（异步补偿，订单状态 ≠ 合同状态）
- 合同 PDF 路径走对象存储抽象层（本周用本地 + 路径占位）

## 6. 依赖与风险

- 依赖：现有订单服务、reportlab、admin-h5（ADMIN-V2 骨架）
- 风险：vendor 未接入 → 保单号本周全为 PENDING，下迭代回填；用户端无真实签字 → 法务合规性下迭代补

# PRD-003: Top3 — AI 就诊准备包

> **状态**: 骨架 v0.1（PM 凝光出）
> **本周交付边界**: 后端 API 骨架 + 数据沉淀通路（高质量 prompt 调优下迭代）

## 1. 业务目标

陪诊订单确认后，AI 基于患者基础信息 + 就诊科室 + 主诉，生成"就诊准备包"：
- 该科室常规检查/化验项目说明
- 患者应携带物品清单
- 主诉相关的可能问诊问题预演
- 注意事项（饮食/用药/陪同人数）

差异化卖点：把"陪诊"从"陪着去"升级为"陪着准备好去"。

## 2. 用户故事

- **U-3-1（用户）**: 下单 1h 内收到 AI 生成的就诊准备包（小程序消息+订单详情）
- **U-3-2（用户）**: 准备包可标记"已完成"项，陪诊师能看到完成状态
- **U-3-3（陪诊师）**: 接单后能看到该单准备包，了解陪诊重点
- **U-3-4（admin）**: 后台能查看任一订单的准备包内容、用户反馈、AI 调用日志

## 3. 功能范围（本周交付）

### 3.1 必交付（代码 done）
| 模块 | 内容 | 边界 |
|---|---|---|
| 准备包数据模型 | `consultation_prep_pack` 表（订单关联、内容 JSON、状态、AI 模型版本、生成时间） | 表+API |
| AI 生成任务 | 下单确认 → 触发异步任务调 AI 生成准备包 | 走现有 AI 调用层（已有），prompt v1 |
| 准备包渲染接口 | 结构化返回：检查清单/携带清单/问诊预演/注意事项 4 大块 | API 契约固定 |
| 已完成标记 | 用户勾选项 → 写入 `checklist_progress` | 简单计数，不做强提醒 |
| 推送通知 | 准备包生成完成 → 微信模板消息/订阅通知 | 走现有通知通路 |
| admin 查询 | 按订单号查准备包内容 + AI 调用 trace | admin-h5 |

### 3.2 下迭代（非本周）
- prompt 精调 + 科室分类模板库
- 多轮对话式问诊预演
- 用户反馈打分 → prompt 迭代闭环
- 准备包 NPS 度量看板

## 4. 验收标准

| AC | 标准 | 验证方式 |
|---|---|---|
| AC-1 | 下单确认后 1h 内 `consultation_prep_pack` 记录生成 | e2e + 异步队列监控 |
| AC-2 | 准备包内容包含 4 大块字段，每块非空 | 单元测试断言 |
| AC-3 | 准备包 API 响应 P95 < 500ms（生成异步、读取快） | 性能测试 |
| AC-4 | 用户勾选已完成项后 1s 内状态持久化 | 单元测试 |
| AC-5 | 微信模板消息成功率 ≥ 95%（10 单灰度） | 通知日志 |
| AC-6 | admin 能查到任一订单的 prep_pack JSON + AI 调用 trace_id | admin-h5 |
| AC-7 | AI 调用失败有重试 + 兜底文案（不阻塞订单流转） | 故障注入测试 |
| AC-8 | 9 字段契约不漂移 | CI 检查 |

## 5. 非功能要求

- AI 单次调用成本 < ¥0.5（用现有模型层默认配置）
- 准备包生成失败率 < 5%（失败有兜底文案降级）
- 异步任务队列堆积告警阈值：100 单

## 6. 依赖与风险

- 依赖：现有 AI 调用层、异步任务队列、微信通知通路、订单事件总线
- 风险：
  - AI 输出质量本周用 prompt v1，下迭代再调优——admin trace 必须落，否则无法回看
  - 通知通路依赖现有 outbox 模式（与 BACKLOG-OUTBOX-PATTERN 并行交付，可能短期不可靠）
