## S2-DEV-007 — outbound 修复（`0686ad2`）

### ✅ ADR-0026r1 §2.0-2.4 全对齐

| ADR 条目 | 实现位置 | 评 |
|---|---|---|
| §2.0 状态机时序图 | `CircuitBreaker.record_success/failure/allow_request` | ✅ 全转换齐 |
| §2.1 half-open N 连胜（默认 3） | `half_open_success_threshold` + `record_success` HALF_OPEN 分支 | ✅ |
| §2.2 CB-open 直接 raise 不进 next attempt | wrapper `if not cb.allow_request(): raise RetryableError` | ✅ B3 正确，**不调 record_failure 不计数**，与 ADR §2.2 完全一致 |
| §2.3 httpx 4xx/5xx 分流 | `classify_httpx_exception` helper + 调用约定 try/except 包 raise classify(e) | ✅ + 408/429 也归 retry 是教科书做法 |
| §2.4 配置项暴露 | `outbound_call` 新增 `half_open_success_threshold` / `idle_reset_seconds` 关键字 | ✅ + 向后兼容（旧 provider 不传新参照常工作）|
| §3 acceptance #5 metric Gauge | `outbound_circuit_state` Gauge 新增 + 与旧 `outbound_circuit_breaker_state` 双写 | ✅ + 双写保证灰度期旧仪表板不断 |

### 💭 三处 ADR 没要求但主动加的优化（赞）

1. **IDLE auto-reset**（`idle_reset_seconds = max(60, timeout*10)`）
   - 解决 ADR 没识别的"半夜首请被陈年 failure_count 踩死"故障模式
   - 实现位置：`allow_request` CLOSED 分支前置 check
   - 这是真问题，胡桃主动加分

2. **HALF_OPEN 任一 failure → `failure_count = threshold`**（不是 `+1`）
   - 保证 reopen 后即使 record_failure 再触发 allow_request 也不会因 count 不够而错走 CLOSED 路径
   - 语义更稳，加分

3. **Prometheus `_get_or_create_<metric>` helper**
   - pytest 反复 import outbound.py 不再 `Duplicated timeseries` 报错
   - 与 P0-06 `payment_metrics._get_or_create_counter` 同模式 — 工程一致性好

### 🟡 1 个观察（不阻塞，记备注）

**HALF_OPEN 并发探测未串行化**：`allow_request` HALF_OPEN 直接 `return True`，没有"只放一个探测"的 lock。Commit 说"caller serialises naturally via await" — 单 worker 单协程下成立，**多 uvicorn worker 下每 worker 各自 CB**，故障下游 timeout=60s 恰好时多 worker 同时进 half-open 会发起 N×3 探测请求。

这本是 ADR-0026 既有 per-process CB 架构假设，不是 S2-DEV-007 引入的新问题。**真要解决要走 Redis 共享 CB state**，那是另一份 ADR（建议进 `BACKLOG-DISTRIBUTED-CB`，触发条件：单下游探测风暴打挂的事故出现）。

### 💭 4 处后续微调（W20 灰度前 or 后）

- 灰度第一周关注 `outbound_circuit_state{provider="deepseek"}` 与 `outbound_call_total{outcome="circuit_open"}` 联动曲线，确认"恢复慢一些"在可接受范围
- `outbound_call_total{outcome="non_retryable"}` 监控 4xx 比例突增（caller bug 早预警）
- 灰度后可酌情调 deepseek 的 `circuit_timeout=30`（成本敏感）/ wxpay 的 `half_open_success_threshold=5`（金钱敏感）

## S2-DEV-001 — OrderShareToken + AIDigest 数据模型（`001e41c`）

### ✅ ADR-0036 §2.3 全对齐

| ADR 条目 | 实现位置 | 评 |
|---|---|---|
| Token UNIQUE + 32 chars URL-safe | `generate_token = token_urlsafe(48)[:TOKEN_LENGTH_CHARS]` | ✅ 熵充足（48 字节 → ~64 chars 截 32，剩 192 bit） |
| 默认 24h 过期 + 7d 硬上限 | `compute_expires_at` `min(candidate, hard_cap)` | ✅ 完美对齐 ADR §2.3 |
| 每订单 active token cap=3 | `create_with_active_cap` revoke 最老 | ✅ + 用 `revoke` 不 `delete`，**保留 audit + WS close 4013 触发链路**，架构师视角加分 |
| `share_scope` enum full/progress_only | `ShareScope` + 默认 full | ✅ |
| 访问聚合字段 first/last/distinct | `OrderShareToken` 列 + `record_access` 方法 | ✅ |

### ✅ AIDigest 金钱安全

`cost_yuan: Numeric(10, 4)` + `Decimal("0.0000")` 默认 —— **不浮点不 float**，与 PaymentService Decimal 风格一致。生产灰度期日成本统计精度有保障。

### 💭 2 处主动收口（赞）

1. **`record_access` 用 first_accessor_openid 近似 distinct count + 注释明示留 S2-DEV-006 实现 precise 计数**
   - 当前实现只能识别"=首位 / ≠首位"，会少计第 3+ 位不同 openid 的 distinct
   - 但 **正确判断**：本 task scope 是数据层骨架，precise 24h-rolling-window distinct 需要扫 WS-access logs，本来就是 S2-DEV-006 调度器 task 的活
   - 注释直接写 "the precise 24h-rolling-window distinct count belongs to the S2-DEV-006 scanner" —— 把"已知缺陷"显式 link 到下游 task，避免被人当 bug 重新发现

2. **`revoke_by_id` bulk-revoke 返回 rowcount**
   - API 层调用时可区分"成功撤销 / token 不存在 / 已撤销"三态，不需要先 SELECT 再 UPDATE
   - 是 W20-D1 后续 S2-DEV-002 REST 端点 `DELETE /api/v1/orders/{order_id}/shares/{token_id}` 的最佳实现底座
