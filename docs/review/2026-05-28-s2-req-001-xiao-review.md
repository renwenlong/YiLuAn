## 四、需要补充的 1 项（非阻塞，可在 develop 阶段补 ADR）

### 💭 F2 OTP 兜底通道的速率限制

ADR §2.2 写了"iOS App / 外部浏览器 → 降级为 OTP 路径（复用现有 Aliyun SMS Provider）"，但 PRD F2 没有写这条路径的**速率限制 / 滥用防护**。

share token 是匿名访问入口，OTP 通道如果不限频会被刷短信：
- 同 token / 24h 内 OTP 发送次数硬上限（建议 5 次）
- 同手机号 / 1h 内被绑定到不同 share token 次数硬上限（建议 3 次，防号池滥用）
- 失败 → 转客服通道（不再无限重试）

**建议**：PRD §6.A 加 acceptance #13.5（编号你定）：
> "F2 OTP 兜底通道速率限制：单 token / 24h 内 ≤ 5 次发码；单手机号 / 1h 内 ≤ 3 个不同 token 绑定；超限触发客服转人工"

不阻塞 review 通过，可在 PRD `v1.1` 或 develop 阶段补；但**上线前必须落地**，否则 ADR-0035 §3 P0-A outbound 修复完后 SMS 通道仍会被刷成本。

## 五、3 处微调（不阻塞）

1. **§8 排期 W20 「并行 ~15d 人天，紧但可达」**：建议明确**关键路径是后端**（5d），三端并行后两端各 3-4d 在后端骨架就绪后才能完整联调。**建议 W20 拆为：W20 D1-D3 后端 OpenAPI freeze + share token 模型 / D4-D10 三端并行 + 联调 / D11-D14 灰度**。这不改总工时，只是把"并行"写成"分阶段并行"，让甘雨排板更好对节奏。

2. **acceptance #4「家属点击链接首次加载 ≤ 2s（4G 网络）」**：建议加测量基准：「P95 ≤ 2s，P50 ≤ 1s」。单纯 ≤2s 没有分布约束，刻晴判 done 时会无据可依。

3. **§9 风险表「微信 jscode2session 频控」**：建议把"依赖 W19-03（P0-04 outbound 装饰器修复）"前置成**硬依赖声明**——P0-04 不收口，PRD F2 不进灰度。这条已经隐含在 ADR-0036 §4 风险 #1，PRD 显式锁一次更稳。
